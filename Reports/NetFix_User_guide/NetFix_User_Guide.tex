\section{Platform Overview and Role-Based Routing}
% =========================================================
The \textbf{NetFix Unified Telecommunication Platform} brings two independent engineering workspaces into one web application:

\begin{guidebox}{Two engineering workspaces}
\textbf{Drive Test Intelligence / Anomaly Portal} combines statistical anomaly detection, Histogram Gradient Boosting ML, PyTorch LSTM temporal validation, a 34-reason deterministic Root Cause Analysis (RCA) engine, interactive Leaflet GIS mapping, and the local \textbf{Penguin AI} assistant.

\medskip
\textbf{5G Network Planning Portal} performs spatial geometry analysis, neighbor-graph validation, and constraint-based planning of 5G NR PCI and RSI while enforcing Mod3 and Mod4 conflict rules.
\end{guidebox}

The datasets used by these workspaces are handled independently. The common platform layer provides authentication, role routing, user experience, persistence, reporting, and AI-assisted interaction.

\subsection{Role-based routing}
\begin{itemize}
  \item \textbf{Optimization Engineer} $\rightarrow$ Drive Test Intelligence dashboard at \texttt{/dashboard}.
  \item \textbf{Planning Engineer} $\rightarrow$ 5G Network Planning Portal Upload \& Plan workspace at \texttt{/np-upload}.
\end{itemize}

\begin{workflowbox}{Quick start}
\textbf{Optimization workflow:} Sign in $\rightarrow$ Upload dataset $\rightarrow$ Wait for the four pipeline stages $\rightarrow$ Review dashboard $\rightarrow$ Open an incident $\rightarrow$ Run RCA $\rightarrow$ Inspect map / Penguin AI / report.

\medskip
\textbf{Planning workflow:} Sign in $\rightarrow$ Upload workbook $\rightarrow$ Inspect clashes $\rightarrow$ Bulk replan or add a site $\rightarrow$ Validate assignments $\rightarrow$ Export the final workbook.
\end{workflowbox}

\section{Drive Test Intelligence and Troubleshooting Portal}
% =========================================================
\begin{guidebox}{Target user: Optimization Engineer / RF Performance Specialist}
This section documents the operational workflow of the NetFix anomaly-detection and RCA portal, including navigation, telemetry monitoring, dataset ingestion, deterministic RCA, GIS inspection, AI-assisted analysis, reporting, and session history.
\end{guidebox}

\subsection{Navigation and workspace layout}
The portal uses a persistent dark navigation sidebar and a light analysis workspace. The main entries are:

\begin{itemize}
  \item \textbf{Dashboard} --- telemetry overview, KPI cards, severity distribution, and backend validation figures.
  \item \textbf{Upload Dataset} --- raw \texttt{.pkl} ingestion, four-stage progress tracking, and recent-session audit.
  \item \textbf{Results} --- deterministic RCA, telemetry evidence, standards references, and recommended actions.
  \item \textbf{Interactive Map} --- Leaflet GIS trajectory, cell/tower context, and anomaly markers.
  \item \textbf{Reports} --- diagnostic summaries and exported analysis outputs.
  \item \textbf{Penguin AI} --- local LLM engineering copilot for grounded analysis and report generation.
  \item \textbf{History} --- historical sessions, completion states, anomaly counts, and cause-matching status.
  \item \textbf{Settings} --- threshold defaults, model preferences, and API configuration.
\end{itemize}

The bottom-left user badge shows the authenticated engineer, current role, and logout controls.

\subsubsection{Execution stages}
\begin{enumerate}
  \item \textbf{File Upload} --- validates the payload and receives the raw \texttt{.pkl} drive-test file.
  \item \textbf{Data Cleaning} --- executes the 11-stage non-leaking preprocessing pipeline (\texttt{ran-cleaning-}\allowbreak\texttt{service}).
  \item \textbf{Anomaly Engine} --- runs the 19-stage statistical, HGB ML, and PyTorch LSTM anomaly-fusion workflow.
  \item \textbf{Results Ready} --- builds MongoDB session indexes and prepares RCA cause matching and GIS artifacts.
\end{enumerate}

On success, the page confirms pipeline completion and the incident count. \textbf{View Anomalies \& Map} opens the investigation workspace; \textbf{Reset Status} prepares the interface for a new upload.

The Recent Analysis Sessions table records dataset name, anomaly count, timestamp, pipeline state, and a direct session-view action.

\subsubsection{Recommended actions and standards grounding}
\begin{enumerate}
  \item Check the antenna / RF path at concentrated eNodeBs, including cross-polarization discrimination and antenna spacing / correlation.
  \item Check UE-side MIMO capability and reporting if the behavior is UE-specific rather than site-specific.

\end{enumerate}

\section{5G Network Planning Portal}
% =========================================================
\begin{guidebox}{Target user: 5G RF Planning Engineer / Network Deployment Specialist}
The 5G Network Planning Portal supports workbook ingestion, clash auditing, automated bulk replanning, interactive site addition, assignment review, before/after Voronoi comparison, AI-assisted network Q\&A through the OCTO copilot, and export of deployment-ready planning parameters.
\end{guidebox}

Every antenna on every tower in a 5G network must be assigned a small set of unique identifiers (PCI, RSI, PRACH root sequences) so that user equipment does not confuse nearby cells. The 5G Network Planning Portal automates that assignment, renders the full network on an interactive map, flags every clash it detects, and lets the engineer replan, add sites, and export the final workbook.

\subsection{Step 1: Sign in and open the Planning workspace}
\begin{enumerate}
  \item Open the portal in the browser and enter the engineer credentials.
  \item Select \textbf{5G Network Planning} from the workspace selector at the top of the sign-in form (the alternative \emph{Drive Test \& Anomaly} workspace routes to the Optimization dashboard covered in Section~2).
  \item Click \textbf{Sign In}. The application routes the Planning Engineer to the \textbf{Upload \& Plan} screen.
\end{enumerate}

\subsection{Step 2: Load a network-planning workbook (Upload \& Plan)}
The Upload \& Plan page is the mandatory entry point --- no other tab is enabled until a workbook has been loaded. Two ingestion modes are supported through separate tabs at the top of the page:

\begin{itemize}
  \item \textbf{Raw} --- for workbooks that list sites, sectors, and antennas but where PCI / RSI have not yet been assigned. After uploading, click \textbf{Run} to let the constraint solver assign all identifiers automatically. A staged progress indicator reports each phase of the pipeline. On completion, the page shows a pass/fail summary and enables the download of the completed workbook.
  \item \textbf{Final} --- for workbooks that already contain a full set of assignments. Click \textbf{Use workbook} to load it directly for review, clash auditing, and exploration; no planning step is required.
\end{itemize}

The same page also includes a built-in \textbf{column reference guide} explaining every required column in plain language, with an example value for each, and a button to download a blank template.

\subsection{Step 4: Investigate conflicts (Clashes)}
The \textbf{Clashes} tab is where every issue flagged on the Planning dashboard is investigated. The map on this tab looks similar to the Planning map, but every sector is coloured by \emph{clash type} rather than by region. Coloured filter chips above the map toggle individual clash categories on and off, and a \textbf{Colour sectors by} selector on the right switches the map shading mode.

Clicking any sector on the map opens a right-hand panel with three modes:
\begin{itemize}
  \item \textbf{Measure} --- displays every neighbouring site inside an adjustable radius; useful for understanding why two sectors have been flagged as too close.
  \item \textbf{Explainer} --- accepts any sector / antenna identifier and returns a short readable summary of whether the sector has an issue and exactly which neighbour is causing it.
  \item \textbf{Clash Inspector} --- opens below the map when a sector wedge is clicked, listing every rule the sector is breaking with a plain-language justification.
\end{itemize}

A \textbf{``Show full clash reference''} link below the map expands a glossary of every clash type the engine can detect, with a short plain-English explanation of each.

The four principal clash categories exposed on this page are:
\begin{itemize}
  \item \textbf{PCI collision (hard):} same PCI assigned to adjacent sectors within the configured reuse distance.

  \item \textbf{Mod3 / Mod30 warnings (soft):} PSS / SSS symbol-shift conflicts.
  \item \textbf{RSI collision (hard):} PRACH root-sequence contention.

\subsection{Step 7: Ask the OCTO copilot}
The \textbf{OCTO} tab exposes an in-workspace \textbf{AI agent} that answers plain-English questions grounded on the currently loaded network. Unlike a plain chatbot, OCTO follows an agentic loop:

\begin{enumerate}
  \item \textbf{User input} --- the engineer types a natural-language question (for example, ``How is the Sinai region doing?'').
  \item \textbf{LLM reasoning} --- the underlying large language model interprets the question, decides which piece of network information is needed, and selects the most suitable \emph{tool} from its registered toolset.
  \item \textbf{Tool invocation} --- the selected tool is executed against the currently loaded network (for example, a site lookup, distance query, clash inspection, or regional summary), returning structured data.
  \item \textbf{LLM answer generation} --- the LLM takes the raw output returned by the tool and composes a plain-English, engineer-friendly answer for the user.
\end{enumerate}

Questions typical of a planning engineer include:

\begin{itemize}
  \item ``Why does site ALX3282 have a problem?''
  \item ``How is the Sinai region doing overall?''
  \item ``What are the five worst sites in my network?''
  \item ``How far apart are these two sites?''
\end{itemize}

Whenever OCTO invokes a tool to answer, it displays an expandable \emph{tool call} chip in the conversation so the engineer can inspect exactly which tool was called, what arguments were passed, and what raw data was returned --- keeping every AI-generated answer fully transparent and auditable. A right-hand \textbf{Toolset} panel lists every capability the agent can invoke, grouped by category (site lookup, clash inspection, distance queries, regional summaries, ranking, etc.).

\subsection{Step 8: Compare planning revisions (Voronoi Compare)}
The \textbf{Voronoi Compare} tab lets engineers compare an older revision of the network against the currently loaded version, focused on a specific site and its neighbourhood.

\begin{enumerate}
  \item Upload the older \texttt{.xlsx} revision using the upload box at the top of the tab.
  \item Select the site of interest and choose how many neighbouring sites to include in the comparison using the dropdown and slider.
  \item Switch between \textbf{Diagram} view (simplified, colour-coded Voronoi cells) and \textbf{Real map} view (accurate map with real sector positions) using the toggle.
  \item A status badge at the top of the comparison reports the outcome as \textbf{Improved}, \textbf{Fully Solved}, \textbf{Unchanged}, or \textbf{Regressed}.
\end{enumerate}

\subsection{Step 9: Export the deployment-ready workbook}
At any point once the network has been loaded and validated, use the \textbf{Download} action on the Upload \& Plan tab (also available in the application footer) to export the current workbook, including every PCI / RSI assignment produced by the solver, ready for deployment and commissioning.

\begin{warningbox}{Before exporting}
Confirm that all hard validation rules pass, review any remaining soft warnings on the Planning and Clashes tabs, and verify that the Assignments table reflects the intended site / sector configuration.
\end{warningbox}
