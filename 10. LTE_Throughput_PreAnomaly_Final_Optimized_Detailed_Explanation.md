# Detailed Technical Explanation — Notebook 10
## `10. LTE_Throughput_PreAnomaly_Final_Optimized.ipynb`
### Cleaning, Canonical Feature Engineering, Causal Context Features, and Pre-Anomaly EDA

---

## 1. Purpose of this notebook

This notebook is the **data-engineering and pre-anomaly foundation** of the LTE downlink throughput anomaly-detection pipeline. Its job is not to make the final anomaly decision. Instead, it transforms raw drive-test data into a clean, auditable, leakage-safe feature table that the anomaly-detection notebook can trust.

The notebook is designed around several principles:

1. **Preserve telecom meaning before simplifying the data.** Important LTE, identity, location, event, activity, radio, scheduler, and throughput fields are protected from aggressive missing-value pruning.
2. **Do not globally impute missing telecom KPIs.** A missing SINR, BLER, CQI, RB, or SCell field should not silently become an invented value before anomaly logic is applied.
3. **Build one canonical LTE-DL schema.** Raw drive-test exports can contain duplicate or vendor-specific names for the same concept. The notebook maps them into stable names such as `actual_lte_dl_throughput`, `lte_rsrp`, `lte_sinr`, `lte_cqi`, `lte_mcs`, and `lte_bler`.
4. **Separate causal ML features from offline RCA context.** Past-only event windows are allowed into forecasting models. Symmetric ±time windows are retained only as post-detection context because they may include future information.
5. **Respect the verified one-second sampling interval.** Time-based reasoning in later notebooks is therefore interpretable as sample-based reasoning at 1 sample = 1 second.
6. **Produce a clean pre-anomaly table with no anomaly-score leakage.** The downstream notebook should start from measurements and context, not from previously generated anomaly labels or expected-throughput outputs.

The main product is a clean LTE downlink modeling table that can be used by both statistical and ML anomaly methods without mixing final anomaly outputs into the input features.

# 4. Global configuration and why it matters

The notebook centralizes important assumptions instead of scattering “magic numbers” throughout the code.

## 4.1 Missingness threshold

```text
MISSING_THRESHOLD_PCT = 70
```

Columns above this missingness level may be removed **unless they are protected telecom fields**.

This threshold is not used blindly. A field such as SCell SINR may naturally be sparse because secondary carriers are not always active. Dropping it solely because it is sparse could remove the exact evidence needed for CA-related RCA.

## 4.2 Fully missing protected fields

The configuration allows fully missing protected fields to be dropped. A column that is 100% missing in the current dataset contains no information for this run, even if its name belongs to a protected telecom family.

The important distinction is:

- **highly missing but informative when present** → often retain;
- **100% missing** → safe to remove for this dataset.

## 4.3 Throughput reference values

The notebook defines several throughput constants used later for EDA and shared downstream configuration, including a fixed low-throughput reference of 10 Mbps and expected-throughput reference values.

Notebook 10 itself does not finalize anomalies from these values. It uses them mainly for visual and descriptive validation, while Notebook 11 applies the actual statistical and fusion logic.

## 4.4 Radio-quality bins

The notebook defines interpretable LTE radio bins:

### RSRP

- Poor: `< -120 dBm`
- Fair: `[-120, -100)`
- Good: `[-100, -90)`
- Excellent: `>= -90`

### RSRQ

- Poor: `< -20 dB`
- Fair: `[-20, -15)`
- Good: `[-15, -10)`
- Excellent: `>= -10`

### SINR

- Poor: `< 0 dB`
- Fair: `[0, 10)`
- Good: `[10, 15)`
- Excellent: `>= 15`

These bins are not “anomaly truth.” They are explanatory radio-condition categories used to study how throughput changes with RF quality and to support later RCA reasoning.

## 4.5 RB reliability requirements

Resource-block evidence is treated carefully because RB fields may be missing, constant, incorrectly exported, or semantically different across tools.

A candidate RB field is considered reliable only when it has sufficient coverage and variation, approximately:

```text
non-null ratio ≥ 70%
unique values ≥ 10
```

This prevents downstream logic from pretending that resource demand is known when the drive-test export does not support that conclusion.

# 8. Protected-column logic

A central risk in automatic cleaning is deleting a sparse but operationally essential field.

The notebook therefore defines:

1. **exact protected column names**, and
2. **protected name patterns**.

Protected concepts include, where present:

- session/test identity;
- IMSI/session metadata;
- timestamp;
- route/location;
- activity;
- events;
- LTE serving/primary/secondary cell KPIs;
- throughput;
- RB and bandwidth fields;
- RACH information;
- HTTP/physical-test information;
- selected extra KPIs.

The decision rule is approximately:

```text
100% missing                         → remove
>70% missing and NOT protected       → remove
constant/single-value and NOT protected → remove
otherwise                            → retain
```

This is intentionally conservative for telecom fields.

# 9. Why the notebook does not globally impute telecom measurements

There is no global step such as:

```text
fill every missing numeric KPI with 0
```

That would be dangerous.

Examples:

- Missing SINR is not equivalent to 0 dB.
- Missing BLER is not equivalent to 0% BLER.
- Missing RB usage is not equivalent to zero scheduler allocation.
- Missing SCell metrics may mean no SCell was active, not that the SCell had “zero” quality.

Instead, downstream methods either:

- work only where a KPI is available;
- use explicit missing categories;
- apply model-specific imputation inside a training fold;
- or fall back to broader reference groups.

This preserves semantic honesty.

# 10. Session and test-identity parsing

The raw `id` field can contain packed information such as IMSI, route/test labels, timestamps, and test type.

The notebook parses this metadata into structured columns where possible, including concepts such as:

- IMSI;
- session/test time;
- route label;
- log time;
- location label;
- test type.

This is important because later operations depend on a correct session boundary.

For example:

- throughput lags must never cross from one session into another;
- rolling comparisons must be grouped by session;
- train/test splitting must keep whole sessions separated;
- episode consolidation is session-aware.

A wrong session identifier can create temporal leakage even when the ML code itself is correct.

# 11. Timestamp normalization and temporal structure

The notebook parses the timestamp, sorts data by session and time, and constructs timing metadata such as:

- date;
- hour;
- minute;
- `sample_gap_seconds`;
- `session_elapsed_seconds`.

The project has verified that the measurements are spaced exactly one second apart. Therefore:

```text
1 row step ≈ 1 second
5 past samples ≈ 5 seconds
10 past samples ≈ 10 seconds
20-step LSTM history ≈ 20 seconds
```

Even with a verified cadence, the explicit `sample_gap_seconds` field remains useful for quality control. It can reveal broken sequences if a future dataset violates the assumption.

# 12. Location handling

Latitude and longitude are converted to numeric form and validated.

The notebook computes previous coordinates within the same session and calculates geodesic movement using the haversine formula.

For two points with latitude/longitude in radians, the haversine distance is based on:

\[
a = \sin^2\left(\frac{\Delta\phi}{2}\right)
  + \cos(\phi_1)\cos(\phi_2)
    \sin^2\left(\frac{\Delta\lambda}{2}\right)
\]

\[
d = 2R\arcsin(\sqrt{a})
\]

where \(R\) is Earth’s radius.

The notebook avoids calculating movement across a session boundary. This matters later when episodes/incidents are geographically consolidated.

# 20. The critical distinction: causal event features vs symmetric RCA windows

This is one of the most important parts of Notebook 10.

For each event family, the notebook creates **two different types of proximity feature**.

## 20.1 Past-only causal windows

Examples:

```text
handover_failure_count_prev10s
near_handover_failure_prev_flag
measurement_report_count_prev5s
near_measurement_report_prev_flag
```

Conceptually, for a target time \(t\), a causal count is:

\[
N_{past}(t; W) = \#\{e: t-W \le t_e \le t\}
\]

Only events that occurred at or before the target timestamp are used.

These are eligible for causal forecasting because they do not reveal the future.

## 20.2 Symmetric ±windows

Examples:

```text
handover_failure_count_pm10s
near_handover_failure_flag
```

Conceptually:

\[
N_{sym}(t; W) = \#\{e: t-W \le t_e \le t+W\}
\]

This is useful for offline RCA because an event occurring shortly *after* a throughput degradation may explain what happened around the incident.

However, it is **not causal forecasting information** because it can contain future events relative to the target sample.

## 20.3 Why both are retained

The pipeline needs both questions:

### Prediction question

> “Using only information available up to this second, what throughput would we expect?”

Use past-only features.

### RCA question

> “What events happened around this anomaly, before or after it?”

Use symmetric context.

The notebook saves an event-feature causality audit that explicitly categorizes features so Notebook 11 can enforce this rule.

# 22. Pre-anomaly exploratory data analysis

EDA is performed before anomaly labels are generated so the analyst can understand the natural distribution of the data.

## 22.1 Throughput quantiles

The notebook calculates quantiles such as:

```text
P1, P5, P10, P17, P25, median, P75, P90, P95, P99
```

and proportions below useful descriptive values such as 5, 10, 15, and 20 Mbps.

These statistics are important later because the statistical anomaly methods intentionally include distribution-derived thresholds such as P10, IQR, and MAD rather than relying only on fixed domain thresholds.

## 22.2 Why P10 matters here

P10 means that approximately 10% of observations lie at or below that throughput level in the relevant reference population.

It answers:

> “What does the lower tail of this dataset actually look like?”

It is not automatically “10 Mbps.” Depending on the route/test population, P10 could be much higher or lower.

This is why Notebook 11 later retains both:

- a fixed 10 Mbps operational anchor, and
- empirical low-tail methods such as P10, IQR, and robust MAD.

For the selected reliable RB usage field, the notebook calculates empirical quantiles such as:

\]

It then builds demand states approximately like:

```text
low              ≤ Q25
```

The exact labels are used to create concepts such as:


Why is this essential?

Suppose throughput is 5 Mbps.

### Case A

```text

```

The user may simply not be demanding resources, or the test may not be fully loading the link.

### Case B

```text

```

The network is allocating substantial resources but throughput remains poor. This is much stronger evidence of inefficiency or a bottleneck.

Therefore, resource demand is a **confidence modifier and conditioning variable**, not just another KPI.

# 27. Estimated RB capacity and utilization

The notebook estimates an approximate RB capacity from LTE bandwidth.

The mapping follows standard LTE bandwidth-to-RB sizes, for example:

```text
1.4 MHz → 6 RB
3 MHz   → 15 RB
5 MHz   → 25 RB
10 MHz  → 50 RB
15 MHz  → 75 RB
20 MHz  → 100 RB
```

When aggregate bandwidth is available it is preferred. Otherwise, PCell bandwidth may be scaled by the estimated carrier count.

An approximate utilization metric is then:

\[
RB\ Utilization\% = \frac{Observed\ RB\ Usage}{Estimated\ RB\ Capacity}\times 100
\]

The value is clipped to a broad upper bound for robustness because raw vendor metrics may represent aggregate/count semantics differently.

This estimate is primarily contextual. It should not be interpreted as a perfect scheduler-load measurement without confirming the exact source KPI semantics.

# 28. What happens when RB evidence is unreliable

The notebook does **not** force low-resource conclusions from an unreliable RB field.

Instead, it marks resource reliability explicitly and avoids letting uncertain RB information block all downstream expected-throughput logic.

This prevents a dangerous failure mode:

```text
Bad/missing RB export
    ↓
algorithm concludes “low demand”
    ↓
real anomalies are suppressed
```

The downstream notebook can therefore distinguish:

- reliable high/medium demand;
- reliable low demand;
- unknown/uncertain resource evidence.

# 29. MCS, CQI, BLER, and why they are preserved for RCA

These three KPI families are highly valuable together.

## CQI

CQI represents the UE’s indication of channel quality and suitable transmission conditions.

Low CQI can help explain reduced spectral efficiency.

## MCS

MCS describes the modulation/coding actually selected. Lower MCS generally carries fewer useful bits per scheduled resource.

A low MCS can therefore help explain why high RB usage does not translate into high throughput.

## BLER

BLER indicates block decoding failures/retransmission pressure.

High BLER can destroy effective throughput even when resource allocation is high.

Together, these support interpretations such as:

```text
High RB + low MCS + high BLER
→ resources are being consumed inefficiently, likely due to poor link quality/retransmissions.
```

versus:

```text
High RB + good CQI + strong MCS + low BLER + low throughput
→ throughput is unexpectedly poor despite apparently favorable radio/link adaptation;
  investigate scheduler, capacity, CA/configuration, transport/core/application constraints, etc.
```

Notebook 10 therefore deliberately protects and canonicalizes them so Notebook 11 can use them for both cell ranking and RCA JSON context.

# 34. Step-by-step example

Consider one sample at time `12:00:20`.

```text
RSRP = -92 dBm
SINR = 18 dB
CQI = 13
MCS = 22
BLER = 2%
RB usage = high

EARFCN = 1650

CA change at 12:00:23
```

Notebook 10 does **not** declare this an anomaly.

Instead it creates a clean representation:

```text
actual_lte_dl_throughput = 6

lte_sinr = 18
lte_cqi = 13
lte_mcs = 22
```

Symmetric RCA context may include that CA change because it occurred within a ±window:

```text

```

The ML model in Notebook 11 may use only the causal features. The final RCA context may mention the future-nearby CA event after the anomaly is already detected.

That is exactly the intended temporal separation.

# 36. How Notebook 10 supports causal forecasting later

Causal ML requires that every predictor at time \(t\) be knowable by time \(t\).

Notebook 10 contributes by:

1. correctly sorting each session in time;
2. preserving `source_index`;
3. creating past-only event windows;
4. labeling symmetric windows so they can be excluded;
5. avoiding target-derived anomaly outputs;
6. preserving technical KPIs needed for resource-conditioned expected throughput.

Notebook 11 then adds past-only throughput/KPI lags and performs group-aware model fitting.

# 37. Important interpretation notes

## 37.1 One-second cadence does not make centered windows causal

Even though every row is exactly one second apart, an 11-sample **centered** window uses approximately five seconds before and five seconds after the current point.

Therefore:

```text
centered rolling context = offline statistical context
past-only lag/window = causal ML context
```

The sampling regularity simplifies timing interpretation but does not remove future leakage from centered operations.

## 37.2 Missing is not bad

A missing SCell KPI is not automatically poor SCell performance.

A missing RB value is not zero demand.

A missing event flag is not proof that no event occurred unless the event export is known to be complete.

The notebook keeps these distinctions rather than forcing binary conclusions.

## 37.3 Context features are not anomaly votes

Poor RSRP, a nearby handover, CA activation, or high BLER may explain an anomaly. They do not automatically become independent anomaly detectors.

This distinction becomes central in Notebook 11’s fusion design.
