# LTE Downlink Throughput — Notebook 01 Detailed Explanation
## Cleaning, Canonical Feature Engineering, and Pre-Anomaly EDA

This Markdown file explains the first split notebook:

```text
01_LTE_Throughput_Preprocessing_PreAnomaly_Feature_Table.ipynb
```

This notebook is the **clean pre-anomaly preparation stage** of the LTE throughput anomaly-detection pipeline. Its job is to take the raw drive-test export, clean it, preserve important telecom evidence, build canonical LTE-DL features, create pre-anomaly radio/RB/CA/activity/event context, validate the data using exploratory statistics and plots, and export a leakage-safe feature table for the second notebook and future ML work.

The most important boundary is:

```text
Notebook 01 stops before anomaly detection.
```

It does **not** create final anomaly flags, P75 expected-throughput values, anomaly scores, severity labels, RCA handoff rows, or episode summaries. Those belong to Notebook 02.

---

# 1. Big-picture role in the full pipeline

The full pipeline is now split into two notebooks:

```text
Notebook 01
Raw drive-test file
→ cleaning and schema audit
→ canonical LTE-DL feature table
→ radio/RB/CA/activity/event context
→ pre-anomaly EDA and validation plots
→ leakage-safe pre-anomaly feature table

Notebook 02
Clean pre-anomaly feature table
→ statistical anomaly detection
→ expected-throughput P75 references
→ RB-efficiency and underperformance flags
→ scores and severity
→ row-level and episode-level anomaly handoff
```

Notebook 01 therefore prepares the table that can safely feed both:

1. the statistical anomaly-detection notebook now; and
2. the future ML expected-throughput notebook later.

This split is important because expected-throughput outputs, anomaly labels, residuals, and severity scores are target-derived. If they are accidentally mixed into an ML training table, the model may learn from leakage rather than from real network features.

# 2. Conceptual design of Notebook 01

The notebook follows three main rules.

## 2.1 Analyze LTE-DL later, but prepare context now

The first notebook prepares only the LTE downlink branch. It keeps supporting features such as radio quality, resource blocks, carrier aggregation, location, activity context, neighbor context, and event context because these are needed later for anomaly interpretation.

## 2.2 Activity windows are context only

The notebook still parses HTTP/HTTPS/download activity intervals, but it does not use them to define the final anomaly population. The latest design uses:

```text
Main analysis population later = all valid LTE-DL rows
Download activity window = context only
RB usage = stronger demand/resource-confidence signal
```

The reason is that the previous QC summaries showed that throughput medians across active download windows, warmup/cooldown windows, and outside-download contexts were close enough that a hard activity-window filter would remove useful LTE evidence without clearly improving anomaly quality.

## 2.3 RB usage is the main demand/resource-confidence feature

Low throughput is only suspicious in a strong optimization sense when the network allocated enough resources or when radio/event evidence explains the degradation. For this reason, Notebook 01 builds RB quality checks, selects a reliable RB reference column, creates RB usage buckets, and assigns RB demand confidence. Notebook 02 later uses this to avoid over-labeling low-RB rows as unexpected underperformance.

The notebook uses calibrated field-data bins rather than ideal textbook-only bins.

### RSRP bins

| Range | Bin |
|---|---|
| `< -120 dBm` | Poor |
| `[-120, -100) dBm` | Fair |
| `[-100, -90) dBm` | Good |
| `>= -90 dBm` | Excellent |

### RSRQ bins

| Range | Bin |
|---|---|
| `< -20 dB` | Poor |
| `[-20, -15) dB` | Fair |
| `[-15, -10) dB` | Good |
| `>= -10 dB` | Excellent |

### SINR bins

| Range | Bin |
|---|---|
| `< 0 dB` | Poor |
| `[0, 10) dB` | Fair |
| `[10, 15) dB` | Good |
| `>= 15 dB` | Excellent |

These bins are created in Notebook 01 because they are normal explanatory features and are safe for ML. They are not anomaly labels by themselves.

The refined separation between measurement-report events and handover execution/failure is important because measurement reports are frequent and broad. If they are merged with actual handover problems, the event-related context can become too noisy.

The notebook defines two protection mechanisms:

1. `EXACT_PROTECTED_COLUMNS`; and

- session IDs and timestamps;
- location fields;
- LTE serving/primary/secondary-cell measurements;
- throughput-related fields;
- activity fields;
- event fields;
- RACH and timing fields.

The protection rule is important because drive-test files often contain sparse but valuable telecom evidence. A simple missingness filter could accidentally delete important event or CA columns.

## 9.5 `is_protected_column(col)`

Checks whether a column matches exact protected names or regex protected patterns.

# 23. RB reliability and demand logic

This is one of the most important improvements in Notebook 01.

## 23.1 Candidate RB columns

The notebook checks:

```text
lte_rb_count
lte_agg_rb_dl
scell1_rb_count
```

For each, it computes:

| Metric | Meaning |
|---|---|
| `non_null_rows` | Number of non-null rows. |
| `non_null_pct` | Non-null percentage. |
| `unique_values` | Number of distinct values. |
| `min`, `p10`, `p25`, `median`, `p75`, `p90`, `max` | Distribution statistics. |
| `reliable_for_anomaly_evidence` | Whether the column passes reliability thresholds. |

## 23.2 RB reference selection

Preferred order:

```text
lte_agg_rb_dl → lte_rb_count → scell1_rb_count
```

The selected column is stored in:

```text
rb_reference_column
```

The selected value is stored in:

```text
rb_usage_value
```

## 23.3 RB usage buckets

The notebook calculates Q25, Q50, and Q75 of the selected RB reference using all valid LTE-DL rows.

It then labels rows as:

```text
low_rb_usage
below_median_rb_usage
medium_rb_usage
high_rb_usage
missing
```

## 23.4 RB demand confidence

The notebook creates:

| Value | Meaning |
|---|---|
| `high` | RB usage is in the high bucket. |
| `medium` | RB usage is medium or above median. |
| `low_or_uncertain` | RB usage is low. |
| `unknown` | RB evidence is unavailable or unreliable. |

This field is extremely important for Notebook 02. It allows strict underperformance detection to distinguish:

```text
low throughput + high/medium RB → stronger anomaly candidate
low throughput + low RB → demand/resource uncertainty
```

## 23.5 RB utilization estimate

The notebook estimates available RB capacity from bandwidth when available, then computes:

```text
rb_utilization_pct = rb_usage_value / estimated_available_rb × 100
```

This is not final demand truth, but it provides useful context for later RCA and ML.

# 27. Why Notebook 01 is ML-ready

Notebook 01 is designed to become the input stage for future ML expected-throughput modeling.

It is ML-ready because:

1. it exports one clean LTE-DL row-level table;
2. it uses stable canonical feature names;
3. it preserves traceability through `source_index`, `id`, and `timestamp`;
4. it includes domain features such as radio bins, RB demand, CA context, event-window counts, and activity context;
5. it removes anomaly-derived leakage columns;
6. it does not include P75 expected throughput, residuals, scores, severity, or RCA labels;
7. it keeps enough context for session-based train/test splitting later.

Future ML notebooks should start from:

```text
lte_dl_feature_table_clean_pre_anomaly.parquet
```

and must still exclude direct throughput leakage features from predictors when predicting `actual_lte_dl_throughput`.

# 29. Common issues and safeguards

| Issue | Safeguard in Notebook 01 |
|---|---|
| Raw pickle is missing | Raises a clear file-not-found error. |
| Raw pickle contains multiple tables | Selects the largest DataFrame. |
| Telecom columns are sparse | Protected-column logic keeps important sparse evidence. |
| Optional KPI missing | Canonical alias becomes NaN instead of crashing. |
| Event text is noisy | Event families are normalized. |
| Activity windows are not discriminative | Kept as context only, not used as hard filter. |
| RB columns may be missing or weak | RB reliability check decides whether to trust them. |
| Future ML leakage risk | Pre-anomaly leakage guard removes target-derived outputs. |
| Very high throughput values distort plots | Visualization-only clipping is used. |

# 30. Final mental model of Notebook 01

The cleanest way to understand Notebook 01 is:

```text
Raw drive-test data
→ profile columns
→ protect important telecom evidence
→ clean high-missing and non-informative columns
→ parse time, session, location, activity, and events
→ detect canonical LTE throughput and KPIs
→ build all-valid LTE-DL feature table
→ add radio bins, RB demand, CA context, neighbor aggregates, and event windows
→ validate with pre-anomaly statistics and plots
→ remove leakage-like columns
→ export clean pre-anomaly table for Notebook 02 and future ML
```

Notebook 01 is therefore not an anomaly detector. It is the clean, auditable, ML-ready foundation for the LTE throughput anomaly-detection pipeline.
