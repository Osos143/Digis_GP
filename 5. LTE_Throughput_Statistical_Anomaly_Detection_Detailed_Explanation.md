# LTE Downlink Throughput — Notebook 02 Detailed Explanation
## Statistical Anomaly Detection, P75 Expected Throughput, Scoring, and RCA-Handoff Tables

This Markdown file explains the second split notebook:

```text
02_LTE_Throughput_Statistical_Anomaly_Detection.ipynb
```

This notebook starts from the clean pre-anomaly LTE-DL feature table created by Notebook 01. It performs the statistical anomaly-detection stage only. It builds multiple statistical flags, expected-throughput references, RB-efficiency checks, independent trigger families, anomaly scores, severity labels, row-level anomaly tables, episode-level summaries, PCI/session summaries, and post-anomaly QC plots.

The most important boundary is:

```text
Notebook 02 does not train ML models.
```

It is the final statistical baseline before the future ML expected-throughput stage. The ML step should be added later after the statistical outputs are stable and validated.

# 8. Statistical anomaly methods

Notebook 02 implements multiple statistical detectors. Each one catches a different shape of bad throughput behavior.

## 8.1 Method 1 — Fixed low-throughput flag

Flag:

```python
low_tp_fixed_flag = actual_lte_dl_throughput < 10 Mbps
```

Purpose:

- simple;
- explainable;
- useful as a baseline;
- dataset-specific because earlier distributions placed 10 Mbps between the lower tail and the first quartile.

Weakness:

- does not account for radio, RB, CA, or session context.

## 8.2 Method 2 — Global P10 lower-tail flag

The notebook calculates global P10 on all valid LTE-DL rows.

Flag:

```text
actual throughput <= global P10
```

Purpose:

- adapts to the dataset distribution;
- catches the bottom 10% of throughput samples.

Weakness:

- always flags a fixed tail percentage, even if some rows are naturally low because of demand/resource context.

## 8.3 Method 3 — Session P10 lower-tail flag

For each session `id`, the notebook calculates session P10.

Flag:

```text
actual throughput <= session P10
AND session P10 <= 20 Mbps
```

The guard prevents healthy high-throughput sessions from generating broad false positives simply because every session has a bottom 10%.

Purpose:

- detects rows that are low relative to their own session;
- useful when route/session conditions vary.

## 8.4 Method 4 — Robust MAD modified z-score

The notebook applies the modified z-score on:

```python
log_tp = np.log1p(actual_lte_dl_throughput)
```

The modified z-score is:

```text
0.6745 × (x - median) / MAD
```

Flag:

```text
log_tp_modified_z <= -3.0
```

Why log throughput?

Throughput is right-skewed and may contain zeros. `log1p()` compresses high outliers while preserving zero values.

## 8.5 Method 5 — IQR lower-fence on log throughput

The notebook computes:

```text
Q1 = log throughput 25th percentile
Q3 = log throughput 75th percentile
IQR = Q3 - Q1
lower fence = Q1 - 1.5 × IQR
```

Flag:

```text
log throughput < lower fence
```

Purpose:

- robust lower-tail anomaly detection;
- does not assume normal distribution.

## 8.6 Method 6 — Rolling local drop

The function `rolling_stat_by_session()` computes sample-based rolling statistics inside each session.

Main rolling features:

```text
rolling_median_tp
rolling_p25_tp
rolling_count
rolling_tp_gap
rolling_tp_ratio
```

Flag:

```text
rolling_count >= 5
AND rolling_median_tp >= 10 Mbps
AND actual / rolling_median <= 0.50
AND rolling_median - actual >= 5 Mbps
```

Purpose:

- catches local collapses where surrounding throughput is much healthier than the current row.

## 8.7 Method 7 — Sustained low-throughput window

This method catches bad periods instead of single-sample drops.

Flag idea:

```text
rolling_count >= 5
AND (rolling_median_tp < 10 Mbps OR rolling_p25_tp < 5 Mbps)
AND row also has direct low-throughput evidence
```

Purpose:

- detects bad route segments or periods where the entire local window is weak;
- avoids relying only on sudden drops.

## 8.8 Method 8 — Bad-session context

The notebook marks sessions as contextually bad when:

```text
session rows >= 20
AND (
    session median throughput < 10 Mbps
    OR session P25 throughput < 5 Mbps
    OR low-throughput ratio >= 40%
)
```

Important:

```text
bad_session_flag is context only.
```

A row is not anomalous just because it belongs to a bad session.

## 8.9 Method 9 — Sudden previous-sample drop

The notebook compares each sample to the previous sample in the same session.

Flag:

```text
previous throughput >= 10 Mbps
AND current / previous <= 0.50
AND previous - current >= 5 Mbps
```

Purpose:

- catches sharp one-step throughput collapses;
- useful for checking nearby mobility, CA, RACH, BLER, or serving-cell changes.

# 9. Expected-throughput P75 references

P75 means the 75th percentile. In this pipeline, it is treated as a realistic achievable throughput reference under similar conditions.

It is:

```text
higher than the median
less extreme than the maximum
more useful for optimization than a simple average
```

Notebook 02 builds two references:

1. radio-condition P75;
2. RB-conditioned P75.

---

# 10. P75 helper functions

## 10.1 `bootstrap_quantile_ci(values, quantile=0.75, n_boot=80, alpha=0.05)`

Computes bootstrap confidence intervals around the P75 value.

Outputs conceptually include:

```text
p75_ci_low
```

The purpose is not to make the detector probabilistic yet. It is to expose whether a P75 group is stable or uncertain.

1. the row-level table with assigned expected throughput; and

RB-conditioned P75 includes RB usage bucket.

# 14. P75 underperformance logic

## 14.1 Context flags

The notebook keeps context flags before strict gating. These show rows that look suspicious by ratio/gap but may not have reliable P75 or RB demand.

Examples:

```text
underperform_vs_p75_context_flag
underperform_vs_rb_p75_context_flag
p75_underperformance_demand_unknown_context_flag
```

## 14.2 Strict radio-P75 underperformance

Strict radio-P75 underperformance requires:

```text
expected radio P75 >= 25 Mbps
actual / expected <= 0.35
gap >= 15 Mbps
P75 reference reliable
medium/high RB demand if RB data is reliable
```

Output flag:

```text
underperform_vs_p75_flag
```

## 14.3 Strict RB-conditioned P75 underperformance

Strict RB-conditioned underperformance uses the same idea, but with the RB-conditioned expected throughput.

Output flag:

```text
underperform_vs_rb_p75_flag
```

This is often a stronger underperformance signal because it says:

```text
Even after accounting for allocated RB resources, actual throughput is far below the reference.
```

# 15. RB-efficiency anomaly method

Notebook 02 also computes throughput per RB:

```text
throughput_per_rb = actual_lte_dl_throughput / rb_usage_value
```

## 15.1 Reference threshold

It computes a P10 threshold over valid medium/high-RB rows:

```text
rb_efficiency_p10_threshold = P10(throughput_per_rb among medium/high RB rows)
```

## 15.2 Low RB-efficiency high-RB flag

Flag:

```text
medium/high RB usage
AND throughput_per_rb <= rb_efficiency_p10_threshold
AND actual throughput is low
```

Output flag:

```text
low_rb_efficiency_high_rb_flag
```

Purpose:

- detects cases where resources were allocated but throughput conversion was extremely poor;
- helps distinguish resource/demand uncertainty from real inefficiency.

# 16. Low throughput with low RB

Notebook 02 explicitly marks low-throughput rows with low RB usage:

```text
low_tp_low_rb_flag
```

Interpretation:

```text
Throughput is low, but RB demand/resource confidence is low.
```

This is not treated as confirmed unexpected underperformance. It may indicate:

- low offered traffic;
- scheduler/resource starvation;
- congestion-like behavior;
- application/server limitation;
- timing/context issue.

Because of that, low-RB-only cases are capped in score and may be excluded from the stricter RCA handoff subset.

# 17. Trigger families

Raw flags are correlated. For example, fixed low throughput, global P10, robust z-score, and IQR lower fence may all trigger on the same sample. Counting each one as independent evidence would inflate the score.

Notebook 02 groups raw flags into independent trigger families.

## 17.1 Main trigger families

| Family flag | Meaning |
|---|---|
| `low_tp_family_flag` | Any lower-tail low-throughput method fired. |
| `temporal_drop_family_flag` | Rolling local drop or sudden previous-sample drop. |
| `sustained_window_family_flag` | Local window is persistently bad. |
| `expected_tp_family_flag` | Strict radio-P75 or RB-conditioned P75 underperformance. |
| `rb_efficiency_family_flag` | Poor throughput per RB under medium/high RB. |
| `radio_limited_family_flag` | Low/degraded throughput with strong poor-radio evidence. |
| `ca_underperformance_family_flag` | CA active with acceptable radio and weak throughput under confirmed demand. |

## 17.2 Candidate gate

The broad candidate gate is:

```text
is_throughput_anomaly = independent_trigger_count > 0
```

This creates the broad candidate table.

## 17.3 Context-only flags

Some flags help interpretation but do not create anomaly candidates alone:

```text
bad_session_flag
event_related_degradation_flag
underperform_vs_p75_context_flag
underperform_vs_rb_p75_context_flag
p75_underperformance_demand_unknown_context_flag
weak_low_rb_only_candidate_flag
```

# 18. Radio-limited degradation logic

Notebook 02 keeps bad-radio low-throughput cases inside the anomaly system. It does not exclude them.

Radio-limited degradation means:

```text
throughput is low/degraded
AND strong radio evidence exists
```

The strong radio evidence is based on:

- poor RSRP;
- poor SINR;
- high BLER;
- poor RSRQ only when combined with poor SINR.

This is intentional because RSRQ alone can be noisy and less monotonic with throughput.

Output:

```text
radio_limited_degradation_flag
radio_limited_family_flag
```

Interpretation:

```text
This is still a throughput anomaly, but it is probably explainable by radio degradation.
```

---

# 19. CA underperformance logic

CA underperformance means:

```text
CA is active or expected to help
radio is not obviously poor
RB demand exists when RB is reliable
actual throughput is still low versus expected
```

Main controls:

```text
CA_UNDERPERF_MIN_EXPECTED_MBPS = 30.0
CA_UNDERPERF_MAX_ACTUAL_MBPS = 15.0
CA_UNDERPERF_RATIO_THRESHOLD = 0.35
REQUIRE_RB_DEMAND_FOR_CA_UNDERPERFORMANCE = True
```

Output:

```text
ca_underperformance_flag
ca_underperformance_family_flag
```

This flag is intentionally stricter than a simple low-throughput + CA-active condition.

# 21. Continuous anomaly scoring

The score is stored as:

```text
anomaly_score_0_100
```

It combines:

```text
strongest-trigger base score
continuous magnitude score
independent trigger-family bonus
evidence bonus
low-RB cap
soft saturation cap
catastrophic gate
```

## 21.1 Strongest-trigger base score

Examples:

| Trigger | Floor |
|---|---:|
| Any trigger | 15 |
| Fixed low throughput | 25 |
| Sustained low window | 35 |
| Radio-limited degradation | 35 |
| Rolling/sudden local drop | 50 |
| Reliable P75 underperformance | 55 |
| Severe P75 underperformance | 75 |

This prevents obvious cases from receiving very low scores.

## 21.2 Continuous magnitude score

The magnitude score considers:

| Component | Meaning |
|---|---|
| Ratio severity | How low actual/expected is. |
| Gap severity | How large expected minus actual is. |
| Low-throughput severity | How close actual is to zero/very low. |
| Drop severity | How large the local or previous-sample drop is. |
| RB-efficiency severity | How poor throughput per RB is. |

This avoids a purely binary score and improves ranking.

## 21.3 Independent-trigger bonus

Only independent families are counted:

```text
bonus = 5 × log1p(independent_trigger_count - 1)
```

The bonus is capped so the score does not explode from overlapping flags.

## 21.4 Evidence bonus

Evidence bonus may include:

- high RB usage;
- CA active;
- near event context;
- poor radio context.

The bonus is capped because context should help ranking, not create severe anomalies by itself.

## 21.5 Low-RB score cap

If a candidate is mainly low-throughput with low RB and lacks radio/temporal/expected/RB-efficiency evidence, the score is capped by:

```text
LOW_RB_DEMAND_SCORE_CAP = 45
```

The notebook also records:

```text
score_low_rb_cap_applied_flag
score_after_low_rb_cap
```

This directly fixes the previous problem where low-RB low-throughput rows could receive severity that was too high.

## 21.6 Saturation control and catastrophic gate

Scores are softly capped below 100 unless catastrophic conditions are met.

Catastrophic eligibility requires:

```text
actual throughput <= 1 Mbps
expected throughput >= 50 Mbps
medium/high RB usage
at least two independent trigger families
```

This prevents too many rows from saturating at 100.

# 22. Severity labels

Severity is assigned by:

```text
assign_severity_v3(row)
```

Possible values:

```text
Normal
Low
Medium
High
Critical
```

Critical is intentionally difficult to reach. It generally requires:

- very low actual throughput;
- high expected throughput;
- strong actual/expected gap or ratio;
- reliable P75 or RB evidence;
- strong score;
- confirmed medium/high RB for catastrophic-style cases.

The function also uses a low-RB cap to prevent weak demand-uncertain rows from being escalated unfairly.

# 29. How to interpret major anomaly types

## 29.1 `unexpected_underperformance`

Meaning:

```text
Actual throughput is much lower than expected while radio is not obviously poor.
```

Likely investigation direction:

- scheduler/resource behavior;
- hidden congestion;
- transport/application/server limitation;
- CA underutilization;
- unmodeled event/mobility context.

## 29.2 `radio_limited_degradation`

Meaning:

```text
Throughput is low/degraded and radio evidence is poor.
```

Likely investigation direction:

- weak coverage;
- poor SINR/interference;
- high BLER/retransmissions;
- cell-edge behavior.

## 29.3 `rb_efficiency_underperformance`

Meaning:

```text
RB usage is medium/high, but throughput per RB is extremely low.
```

Likely investigation direction:

- poor MCS/CQI efficiency;
- BLER/retransmission;
- scheduler inefficiency;
- hidden transport/application bottleneck.

## 29.4 `rb_conditioned_underperformance`

Meaning:

```text
Even after accounting for allocated RB resources, actual throughput is far below expected.
```

Likely investigation direction:

- inefficient radio link;
- scheduler behavior;
- CA/SCell issue;
- transport limitation.

## 29.5 `ca_underperformance`

Meaning:

```text
CA is active, but throughput remains weak under acceptable radio and confirmed demand.
```

Likely investigation direction:

- weak SCell;
- poor CA utilization;
- CA activation/deactivation instability;
- scheduling/load issue.

## 29.6 `resource_limited_or_demand_uncertain_low_throughput`

Meaning:

```text
Throughput is low, but RB usage is also low.
```

This should not be treated as confirmed unexpected underperformance. It needs careful review because the UE may not have had enough offered demand or scheduled resources.

## 29.7 `sudden_drop` and `rolling_local_drop`

Meaning:

```text
Throughput dropped sharply relative to the previous sample or local rolling baseline.
```

Likely investigation direction:

- handover/mobility;
- CA change;
- RACH/access issue;
- sudden BLER/SINR degradation;
- serving-cell change.

## 29.8 `sustained_low_throughput_window`

Meaning:

```text
The local window is persistently bad, not just one sample.
```

Likely investigation direction:

- bad route segment;
- sustained poor coverage/quality;
- repeated resource limitation;
- persistent cell/sector issue.

# 32. Common issues and safeguards

| Issue | Safeguard in Notebook 02 |
|---|---|
| Wrong input file accidentally used | Load-time leakage guard checks for post-scoring columns. |
| Low-RB rows over-flagged as severe | Low-RB cap and weak low-RB-only suppression. |
| P75 groups too sparse | Fallback hierarchy, group size, confidence labels, CI columns. |
| P75 false positives under low demand | Strict P75 requires medium/high RB when RB is reliable. |
| Too many adjacent row anomalies | Episode grouping converts rows into incidents. |
| Event context too broad | Event proximity is context only, not anomaly trigger by itself. |
| Broad low-throughput labels hide specific cases | Specific-first anomaly type priority. |
| Scores saturate at 100 | Soft cap and catastrophic gating. |
| PCI anomaly counts are misleading | PCI summaries include exposure denominators and Wilson CIs. |
| Duplicate handoff columns | `unique_existing_columns()` protects schema generation. |

# 33. Final mental model of Notebook 02

The cleanest way to understand Notebook 02 is:

```text
Load clean pre-anomaly LTE-DL table
→ verify no anomaly-derived leakage is present
→ compute low-throughput, robust, rolling, sustained, bad-session, and sudden-drop statistics
→ build radio-P75 and RB-conditioned-P75 expected-throughput references
→ compute actual/expected gaps, ratios, residuals, confidence, and CIs
→ detect strict underperformance only when reliability and RB-demand gates pass
→ compute RB-efficiency anomalies
→ group correlated flags into independent trigger families
→ score using magnitude, trigger strength, independent evidence, caps, and catastrophic gating
→ assign severity and anomaly type
→ save broad candidates and stricter RCA handoff rows
→ group row-level anomalies into episodes
→ export QC summaries, PCI/session summaries, schema, audit table, and plots
```

Notebook 02 is therefore the statistical anomaly-detection and handoff layer. It produces high-quality RCA-ready evidence while keeping final RCA decisions and ML modeling as separate next steps.
