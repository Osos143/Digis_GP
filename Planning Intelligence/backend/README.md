# 5G Planning Module — Backend (FastAPI)

This backend exposes the NR5G planning pipeline as HTTP endpoints used by
the 5G Planning Module frontend workspace.

Important design rule: planning logic is not re-implemented here.
`backend/main.py` only orchestrates calls to existing pipeline modules.

---

## Current architecture

### What this service does

- Loads workbook data (`raw`, `final`, and runtime uploaded/generated workbooks).
- Runs full planning (`bulk_plan`) when requested.
- Runs targeted planning for add-site and replan-site flows.
- Builds map/KPI payloads for frontend tabs.
- Provides deterministic clash explanations for sectors.
- Provides a tool-calling AI endpoint grounded in pipeline outputs.
- Serves static clash-type definitions for the Clashes tab reference panel.
- Exposes agent tool metadata and backend model configuration for the UI.

---

### Key backend modules

- `main.py`: FastAPI routes, request/response wiring, error handlers,
  KPI enrichment logic, site editor option computation.
- `workbooks.py`: in-memory workbook registry with stable ids (`raw`,
  `final`, and `live:*`). Resolves paths from multiple candidate
  locations (local `data/`, Streamlit `data/`, `output/`).
- `cache.py`: mtime-keyed cache for pipeline state, network JSON, and
  raw JSON. Supports explicit invalidation after writes.
- `agent.py`: tool-calling agent loop, tool implementations, clash
  definitions dictionary, and backend config accessors.
- `pipeline/*`: planning/validation/export logic shared with the
  Streamlit path, not re-implemented here.

## Workbook model and lifecycle

The backend is stateless in HTTP but keeps a runtime in-memory workbook
registry in `workbooks.py`.

### Built-in workbook ids

| Id | File | Notes |
|---|---|---|
| `raw` | `NR5G_PCI_RSI_Planning_raw.xlsx` | Unplanned, always available |
| `final` | `NR5G_PCI_RSI_Planning_Final.xlsx` | Shipped planned workbook |

### Path resolution order for built-in workbooks

`workbooks.py` tries candidate paths in order and uses the first
existing file:

- `raw`: `backend/data/` → `network_pulse_streamlit/data/`
- `final`: `backend/data/` → `output/` → `network_pulse_streamlit/data/`

### Runtime workbook ids (`live:*`)

Generated by:

- `POST /api/upload` → registers uploaded raw workbook
- `POST /api/upload_final` → registers uploaded planned workbook
- `POST /api/replan` → registers newly planned output
- `POST /api/addsite/new/commit` → registers post-add-site output
- `POST /api/replan_site/commit` → registers post-replan output
- `POST /api/addsite/new/preview` → registers non-selectable preview
  workbook (internal use only, not shown in workbook list)

Notes:

- `live:*` ids do not persist across backend restarts.
- Preview workbooks are registered with `selectable=False` and do not
  appear in `GET /api/workbooks`.
- If a client sends an unknown or stale workbook id, the API returns
  `404` with a recovery message so the frontend can redirect the user.

## Caching behavior (`cache.py`)

All cache entries are keyed on `(path, mtime)`. A workbook file written
or overwritten automatically produces a new cache key on the next
request. Three separate caches exist:

| Cache | Key | Content |
|---|---|---|
| `_PIPELINE_STATE` | `(path, mtime)` | `(sectors, graph, assignments)` tuple |
| `_NETWORK_JSON` | `(path, mtime)` | Full network JSON payload |
| `_RAW_JSON` | `(path, mtime)` | Raw network JSON payload |

`cache.invalidate(path)` explicitly removes all entries for a given path
across all three caches. It is called after every export write so the
next read always reflects the new file.

## KPI summary enrichment (`_enrich_kpi_summary`)

`GET /api/network` and `GET /api/raw` both call `_enrich_kpi_summary`
before returning. This ensures the client always receives a `kpi.summary`
field regardless of workbook state.

### Summary source priority

1. **Validator-derived summary** — populated when the payload already
   carries a `kpi.validation` block from a fresh planning or upload run.
   Hard and soft totals are summed from the validation report dict.
2. **KPI_Report sheet** — `_kpi_summary_from_sheet` opens the workbook
   with `openpyxl` in read-only mode, parses the `KPI_Report` sheet row
   by row, and extracts hard/soft/coverage counts plus `overall result`.
3. **Raw fallback** — if neither source is available, returns
   `{ source: "raw", status: "READY", hard_issues: 0, soft_issues: 0 }`.

This prevents stale sheet values from overriding fresh validator results
since source 1 is always checked first.

### KPI_Report sheet parsing

The parser identifies sections by matching row labels:

- `"Hard Rules (must be 0)"` → starts collecting `hard` dict entries
- `"Soft Conflicts (informational)"` → starts collecting `soft` dict
  entries
- `"Coverage"` → starts collecting `coverage` dict entries
- `"Overall Result"` → reads `status` value

## AI agent (`agent.py`)

The agent implements a pure routing model: the LLM reads the user's
message, picks zero or more tools, the tools compute real values from
the pipeline, and the LLM only phrases the already-computed result.

**Hard rule**: the model never computes a PCI, RSI, Mod4 value,
distance, or count itself. Every number in every tool result comes from
the real pipeline.

### Backend selection

The `run_agent` function accepts a `model` parameter for call-site
compatibility but always uses the Ollama backend. The Claude backend
remains in code (`_run_claude`) but is not reachable from the public
route.

| Backend | Entry point | Protocol |
|---|---|---|
| Ollama | `_run_ollama` | OpenAI-style `tools` param via `/api/chat` |
| Claude | `_run_claude` | Anthropic Messages API native `tools` param |

Both backends run the same `TOOL_IMPLS` dict and the same `TOOL_SPECS`
JSON schema. Only response phrasing differs between them.

### Configuration

| Variable | Default | Effect |
|---|---|---|
| `OLLAMA_URL` | `http://127.0.0.1:11435` | Ollama server address |
| `OLLAMA_MODEL` | `qwen3:4b` | Model pulled on the Ollama server |
| `CLAUDE_MODEL` | `claude-sonnet-5` | Anthropic model (unused in current route) |
| `ANTHROPIC_API_KEY` | (none) | Required only for Claude path |
| `MAX_TOOL_ITERATIONS` | `4` | Maximum tool-call rounds per request |

### Tool loop behavior

Both backends run the same loop:

1. Send message + history + system prompt to the model with tool specs.
2. If the model returns tool calls, execute each via `TOOL_IMPLS`.
3. Append tool results to the message list and loop.
4. If the model returns a text response (no tool calls), return it.
5. If `MAX_TOOL_ITERATIONS` is reached without a text response, return a
   fallback message.

Tool results are truncated to 4000 characters before being appended to
the context to avoid overflow.

### System prompt

The system prompt instructs the model to:

- Use tools for all factual lookups before answering.
- Never invent a PCI, RSI, Mod4, distance, or count.
- Return a plain error string if a tool returns an error.
- Keep answers concise with bold formatting for concrete values.
- Acknowledge what it cannot help with rather than guessing.

### Available tools

| Tool | Description |
|---|---|
| `explain_sector` | Full per-sector conflict breakdown re-derived live from the neighbor graph |
| `region_summary` | Sector/site counts and clash totals for one region |
| `overall_summary` | Network-wide totals, PASS/FAIL, hard/soft counts, PCI/RSI ranges |
| `worst_sites` | Sites ranked by number of clashing sectors, filterable by region |
| `find_sites` | Substring site/sector search returning up to 25 matches |
| `distance_between` | Haversine distance between two sites with collision/confusion range flags |
| `neighbors_within_radius` | All sites within a given radius of a site, sorted by distance |
| `clash_type_info` | Static clash type definition plus optional live per-sector cause |
| `plan_health_score` | Composite 0–100 score for whole network or one region |
| `compare_regions` | Side-by-side stats for two regions in one call |

### Tool implementation details

**`explain_sector`**
Calls `explain.explain_sector` against the live pipeline state. Returns
PCI/Mod4/RSI/Mod3 values and every hard/soft clash with neighbor ids and
distances.

**`region_summary`**
Reads `kpi.regions[region]` from the network JSON. Returns sector count,
site count, and all clash type counts for that region. Valid region codes:
`ALX`, `SIN`, `UPP`, `DEL`.

**`overall_summary`**
Reads top-level KPI fields from the network JSON. Returns total sectors,
total sites, validation result, all hard/soft counts, and PCI/RSI ranges.

**`worst_sites`**
Iterates `data["sites"]`, counts sectors with any of the `c4/cc/cr/cf`
flags set, sorts descending, optionally filters by region, returns top
`n` (default 5).

**`find_sites`**
Uppercases the query and all site ids, returns the first 25 sites whose
id contains the query substring.

**`distance_between`**
Calls `utils.haversine_m`, converts to km, returns both sites, distance,
and boolean flags for whether the pair falls within collision (7 km) or
confusion (14 km) range.

**`neighbors_within_radius`**
Iterates all sites, computes haversine distance from the center site,
returns up to 40 neighbors sorted by distance ascending.

**`clash_type_info`**
Returns a static definition from `CLASH_DEFINITIONS` for the given clash
type, plus live `explain_sector` output if `sector_id` is also provided.
If neither argument is given, returns the entire definitions dict.

**`plan_health_score`**
Computes a 0–100 composite score:

- Starts at 100.
- Subtracts up to 60 points for hard violations (5 points each, capped).
- Subtracts up to 40 points for soft conflict rate (rate × 100, capped).
- Network-wide mode counts PCI collision and confusion as hard violations.
- Region mode uses soft rates only (region breakdown does not carry
  separate hard counts).

**`compare_regions`**
Reads `kpi.regions` for both region codes, returns both stat blocks plus
sector count difference and Mod4 clash rate difference in percentage
points.

### Clash definitions (`CLASH_DEFINITIONS`)

Static dict in `agent.py` covering all clash types. Consumed by:

- `tool_clash_type_info` (agent tool)
- `GET /api/clash_info` (Clashes tab reference panel)
- `GET /api/clash_info/{sector_id}` (per-sector live cause)

| Key | Label | Severity | Threshold |
|---|---|---|---|
| `collision` | PCI collision | Hard — must be 0 | Within 7 km |
| `confusion` | PCI confusion | Hard — must be 0 | Within 14 km |
| `mod4` | Mod4 inter-site | Soft — informational | Within 7 km, different sites |
| `rsi` | RSI reuse | Hard — must be 0 | Within 14 km |
| `mod3` | Mod3 adjacent | Hard — must be 0 | Ring-adjacent co-site sectors |
| `mod4_intra` | Mod4 intra-site | Hard — must be 0 | Ring-adjacent co-site sectors |
| `mod3_non_adj` | Mod3 non-adj reuse | Soft — informational | Non-adjacent co-site sectors |
| `mod4_non_adj` | Mod4 non-adj intra-site | Soft — informational | Non-adjacent co-site sectors |
| `clear` | Clear | n/a | No conflicts |

## Site editor option computation (`_replan_site_editor_options`)

Called by both `POST /api/replan_site/preview` and
`POST /api/replan_site/options`. Computes valid PCI, Mod4, and Mod3
choices for each sector of the target site given the current draft
assignments.

### Algorithm

1. Separate target sector ids from all other (locked) assignments.
2. Merge locked assignments with the draft to form `merged_assignments`.
3. For each target sector sorted by azimuth:
   - Remove the sector's own assignment from the local view.
   - Call `constraints.compute_forbidden_sets` to get forbidden PCI
     values from the neighbor graph.
   - Call `constraints.valid_pci_candidates` to get the full valid PCI
     list.
   - Compute forbidden Mod4 values by inspecting co-site sibling
     assignments via `constraints.mod4_co_site_siblings`.
   - Derive valid Mod3 values from the set of Mod3 values (`pci % 3`)
     across all valid PCIs.
   - Filter the valid PCI list to only those matching the currently
     chosen Mod4 and Mod3 (if chosen by the user).
   - Ensure the currently chosen Mod4/Mod3 appears in the valid lists
     even if technically invalid, to prevent the UI from losing the
     current selection.
   - Call `_rank_pci_suggestions` to produce a ranked shortlist of up
     to 16 PCIs, preferring the current PCI first and then values
     numerically closest to it.

### Mod4/Mod3 guided selection cascade

The editor supports a three-step guided cascade:

1. User picks **Mod4** → only PCIs with that Mod4 are shown.
2. User picks **Mod3** → only PCIs with that Mod4 AND Mod3 are shown.
3. User picks **PCI** from the filtered shortlist.

Each call to `POST /api/replan_site/options` recomputes the full set for
the current draft, so changing one sector's assignments immediately
updates the valid options for all other sectors on the same site.

---

## RSI preservation (`_preserve_existing_site_rsi`)

Both commit flows (add-site and replan-site) call
`_preserve_existing_site_rsi` before writing. This copies the original
RSI value from the pre-existing workbook assignment into the new
assignment dict, preventing the incremental planner from accidentally
overwriting RSI values that were already correct in the base workbook.

## Error handling

### Global exception handlers

Two `@app.exception_handler` decorators in `main.py` intercept common
failure modes and return clean `404` JSON responses instead of `500`
crashes:

| Exception | Cause | Response |
|---|---|---|
| `FileNotFoundError` | Workbook file deleted after registration | `404` with recovery message |
| `ValueError` containing `"unknown workbook id"` | Stale `live:*` id after backend restart | `404` with recovery message |

The `ValueError` handler only intercepts errors where the message
contains `"unknown workbook id"` to avoid masking unrelated value errors
in pipeline code.

### Upload validation

**`POST /api/upload`**

- Rejects non-`.xlsx`/`.xlsm` files with `400`.
- Rejects workbooks where all sectors already have PCI/RSI/Mod4 assigned
  (these should use `upload_final`) with `400`.
- Removes the file from disk on any validation failure before responding.

**`POST /api/upload_final`**

- Rejects non-`.xlsx`/`.xlsm` files with `400`.
- Rejects workbooks where any sector has no PCI assigned, with a count
  of missing sectors included in the error message.
- Removes the file from disk on validation failure before responding.

# API Reference

All endpoints are under `/api`.

## Workbook and Dataset Endpoints

| Method | Path | Description |
|---|---|---|
| `GET` | `/api/workbooks` | All selectable workbook ids and labels |
| `POST` | `/api/upload` | Upload raw (unplanned) workbook |
| `POST` | `/api/upload_final` | Upload already-planned workbook |
| `GET` | `/api/download?workbook=<id>` | Download workbook file by id |

### `POST /api/upload`

- Form-data field: `file` (`.xlsx` or `.xlsm`)
- Validates workbook shape via `loader.load_sectors`.
- Rejects already fully planned workbooks with a descriptive `400`.
- Returns `{ workbook, label, sectors, sites }`.

### `POST /api/upload_final`

- Form-data field: `file` (`.xlsx` or `.xlsm`)
- Loads the workbook as-is with `plan_all=False`.
- Runs `validator.validate` immediately and includes the result in the response.
- Calls `cache.invalidate` after registration.
- Returns `{ workbook, label, sectors, sites, pass, collisions, confusions, mod3 }`.

---

## Planning and Network Data Endpoints

| Method | Path | Description |
|---|---|---|
| `POST` | `/api/replan?workbook=<id>` | Full network planning pass |
| `GET` | `/api/network?workbook=<id>` | Full network payload with KPI enrichment |
| `GET` | `/api/raw?workbook=<id>` | Raw/unplanned network payload |
| `GET` | `/api/sectors?workbook=<id>` | Flat sector rows with all clash flags |
| `GET` | `/api/sectors_raw?workbook=<id>` | Flat sector rows, unplanned rows allowed |

### `POST /api/replan`

- Runs `bulk_plan` → `validate` → `export_results` in sequence.
- Calls `cache.invalidate` on the output path before registering.
- Registers the output as a new `live:*` workbook.
- Returns `{ workbook, written, pass, collisions, confusions, mod3 }`.

### `GET /api/sectors`

- Flattened from `network_json["sites"][*]["sec"]`.
- Includes all clash flag fields: `c4`, `cc`, `cr`, `c3`, `cf`, `c3n`, `c4i`, `c4n`.

### `GET /api/sectors_raw`

- Uses `loader.load_sectors(path, plan_all=False)`.
- Does not run validation.
- PCI/RSI/Mod4 fields may be `null`.
- Used by the Voronoi Compare tab to avoid hard failures on partially planned or differently shaped workbooks.

| Method | Path | Description |
|---|---|---|
| `GET` | `/api/explain/{sector_id}?workbook=<id>` | Sector conflict explanation with narration |

### `GET /api/explain/{sector_id}`

- Calls `explain.explain_sector` then appends `explain.narrate` output as a `narration` string field.
- Returns `404` if the sector id is not found in the workbook.

### `POST /api/chat`

- Body: `{ workbook, message }`
- Calls `assistant_chat.answer` with full pipeline state and network JSON.
- No LLM involved. Responses are deterministic and keyword-based.

## AI Agent Endpoints

| Method | Path | Description |
|---|---|---|
| `GET` | `/api/agent/tools` | Available tool names and descriptions |
| `GET` | `/api/agent/info` | Active model name and URL from backend config |
| `POST` | `/api/agent/chat` | LLM tool-calling agent |

### `GET /api/agent/info`

- Returns `{ model, url }` reflecting the actual `OLLAMA_MODEL` and `OLLAMA_URL` values the backend is running with.
- The UI uses this to display the active model name so it always matches what requests actually hit.

### `POST /api/agent/chat`

- Body: `{ workbook, message, model, history }`
- The `model` field is accepted for call-site compatibility but ignored; the Ollama backend is always used.
- `history` is a list of prior `{ role, content }` message dicts for multi-turn context.
- Returns `{ reply, tool_calls, model }`.
- `tool_calls` contains the full input/result trace of every tool called during the request, useful for transparency and debugging.

# Add Site Workflows

| Method | Path | Description |
|---|---|---|
| `POST` | `/api/addsite/new/preview?workbook=<id>` | Preview new site assignment |
| `POST` | `/api/addsite/new/commit` | Commit new site to workbook |
| `POST` | `/api/replan_site/preview` | Preview replan of existing site |
| `POST` | `/api/replan_site/options` | Recompute editor options for current draft |
| `POST` | `/api/replan_site/commit` | Commit existing site replan |

### `POST /api/addsite/new/preview`

- Query: `workbook=<id>`
- Body: `{ site_id, lat, lon, azimuths }`
- Rejects with `400` if `site_id` already exists in the workbook.
- Copies the workbook to a temp file via `shutil.copy`, appends new sector rows using `_append_new_site_rows`, then runs `add_site`.
- Registers the temp file as a non-selectable `live:*` workbook.
- Returns `{ tmp_id, assignments, neighbors }`.
- `neighbors` lists existing neighboring sectors with their current PCI/Mod4/RSI values.

### `POST /api/addsite/new/commit`

- Body: `{ tmp_id, assignments }`
- Merges the provided assignments with all remaining sectors from the temp workbook, using their existing values for non-target sectors.
- Runs `validate`, exports to `NR5G_PCI_RSI_Planning_live.xlsx`.
- Returns `{ workbook, report }`.

### `POST /api/replan_site/preview`

- Body: `{ workbook, target_site }`
- Calls `add_site` for the target site only.
- Applies `_preserve_existing_site_rsi` to carry forward original RSI values.
- Calls `_replan_site_editor_options` to generate guided editor data.
- Returns `{ old, assignments, neighbors, editor_options }`.
- `old` is the prior assignment dict for the target site's sectors.
- `editor_options` contains `valid_pci`, `suggested_pci`, `valid_mod4`, `valid_mod3` per sector.

### `POST /api/replan_site/options`

- Body: `{ workbook, target_site, assignments, mod3_choices }`
- `mod3_choices` is an optional `{ sector_id: mod3_value }` dict representing the user's current Mod3 selections in the editor.
- Recomputes `_replan_site_editor_options` for the full current draft.
- Returns `{ editor_options }`.

### `POST /api/replan_site/commit`

- Body: `{ workbook, assignments }`
- Loads the base workbook, applies RSI preservation for target sectors, builds full assignments for all sectors, validates, and exports.
- Registers the output as a new `live:*` workbook.
- Returns `{ workbook, report }`.

# Typical End-to-End Flows

## Raw Upload and Full Planning

1. `POST /api/upload` → receive `workbook` id
2. `POST /api/replan?workbook=<id>` → receive new planned `workbook` id
3. `GET /api/network?workbook=<id>` and `GET /api/sectors?workbook=<id>`
4. Optional: `GET /api/download?workbook=<id>`

## Final Upload (Already Planned)

1. `POST /api/upload_final` → receive `workbook` id with validation summary in response
2. `GET /api/network?workbook=<id>` and `GET /api/sectors?workbook=<id>`

## Add a Brand-New Site

1. `POST /api/addsite/new/preview?workbook=<id>` with `{ site_id, lat, lon, azimuths }`
2. Review `assignments` and `neighbors` in the response
3. `POST /api/addsite/new/commit` with `{ tmp_id, assignments }`
4. Use the returned `workbook` id for all subsequent reads

## Replan Existing Site with Guided Editor

1. `POST /api/replan_site/preview` with `{ workbook, target_site }`
2. Review `old`, `assignments`, `neighbors`, and `editor_options`
3. As the user adjusts Mod4/Mod3/PCI selections, call `POST /api/replan_site/options` with updated `assignments` and `mod3_choices` to receive refreshed valid option lists
4. `POST /api/replan_site/commit` with `{ workbook, assignments }`
5. Use the returned `workbook` id for all subsequent reads

## AI Agent Session

1. `GET /api/agent/info` → display active model name in the UI
2. `GET /api/agent/tools` → optionally display available capabilities
3. `POST /api/agent/chat` with `{ workbook, message, model, history }` for each turn, passing the accumulated `history` list for multi-turn context
4. Inspect `tool_calls` in the response for transparency and debugging

# Troubleshooting

- **`404` "file is no longer available"** — the registered workbook file was deleted or the backend restarted with a stale id in the client. Re-upload the workbook and continue from the new id.
- **Agent returns "Couldn't reach Ollama"** — ensure `ollama serve` is running, the model named in `OLLAMA_MODEL` is pulled (`ollama pull qwen3:4b`), and `OLLAMA_URL` points to the correct host and port.
- **`400` "already looks fully planned"** on raw upload — the workbook has PCI/RSI/Mod4 filled in for all sectors. Use `POST /api/upload_final` instead.
- **`400` "looks like a raw workbook"** on final upload — one or more sectors have no PCI assigned. Run planning first or use `POST /api/upload`.
- **Slow first request on a large workbook** — expected. The pipeline state cache is cold on first access and warms after the initial load.
- **`500` on `replan_site/commit` with RSI mismatch** — the base workbook may have changed since the preview was generated. Re-run `replan_site/preview` and commit again from the fresh draft.
